01VulnAgent 当前进度概览

以下事实来自本地仓库勘查（README 标称 V0.4，已合入 V0.5 加壳/混淆还原、V0.6 大模型服务代码审计）。结论先行：工程骨架与多智能体协议在课程设计量级相当扎实，但「真实漏洞战果」这一项与所有对标项目之间存在代差。

架构与工程

多智能体运行时已成型

  • 12 个 Agent：planner / source_audit / binary_analysis / fuzz / verification / reviewer / report / code_audit / code_deobfuscation / program_restoration 等。
  • agent_runtime Supervisor 有界路由，MAX_AGENT_STEPS=15，结构化路由 + 确定性回退。
  • 统一 Schema：Task / AgentMessage / VulnerabilityCandidate / Evidence，发现侧只能产 CANDIDATE，Verification 独占 CONFIRMED/REJECTED。
  • Evidence First；poc/service.py 只生成不联网、不执行目标的受控 replay 脚本。
  • 前端仅 React/Vite 10 文件约 743 行，FastAPI 挂载 dist。
分析能力

静态 / 动态 / 符号三条线都接了

  • Python 深度自研审计 + Semgrep/Bandit 融合。
  • Tree-sitter 覆盖 Go / C / C++，做到 AST、函数内 CFG、函数内污点。
  • PE/ELF/DEX 静态解析、8 类保护识别、IAT 重建、OLLVM 静态还原、自研符号执行引擎。
  • 真实 libFuzzer + ASan 对接（libfuzzer.py 341 行）+ Windows Job Object 隔离。
  • LLM 真实调用对比：DeepSeek / GLM / Kimi，简单样本上 F1 均为 1.0。
评测现状

样本全部是自研教学集

  • 20 个 source + 14 个 binary 自研教学样本，10 次 fuzz 消融，BlindEvaluator。
  • 无真实 ground truth、无真实项目、无真实 CVE 上的发现记录。
  • 加壳/混淆样本 0 finding 或仅 UNCERTAIN；未动态执行。
  • third_party/exploitgym/ 已引入数据集目录，但 README/进度文档无任何在 ExploitGym 上跑通任务的实验报告。
作者自述缺口

作者已承认的短板

  • 深度审计主要覆盖 Python；C/C++/Go 跨函数污点不完整。
  • 无真正网络/文件系统隔离；无跨进程 checkpoint。
  • 从未在真实大型开源项目 / 真实 CVE 上验证过漏洞发现能力。
  • 这几点与下面对标项目的差距方向一致。

02对标项目逐个简介

分两组：A 组为漏洞挖掘 / ExploitGym 生态（主对比），B 组为渗透测试与 LLM+fuzz 趋势（参照）。硬事实以 GitHub / 论文 / 官方博客为准，查不到处标注「未查证」。

A 组 · 漏洞挖掘与 ExploitGym 生态

基准 · 必对标的目标

ExploitGym（UC Berkeley RDI，2026-05）

「已知 bug → 完整武器化 exploit」能力基准，前作 CyberGym 的下游。论文 arXiv:2605.11086。
  • 共 898 个实例：用户态 OSS-Fuzz 520、V8/ClusterFuzz 185、内核 kernelCTF+syzbot 193（内核两类精确拆分未单独公开）。
  • 判定：把 PoV 扩展成读到动态生成的特权 flag，两小时 wall-clock，再由 agent-as-a-judge 确认用的是「指定漏洞」。
  • 官方 baseline：最强 Claude Mythos 仅 157/898（17.5%）；GPT-5.5 120/898（13.4%）。开缓解措施后几乎归零。
  • 对接方式：uv 装依赖 + Docker，拉起 controller/Squid 出站防火墙/LLM proxy 三件套，注入四个 CYBERGYM_* 环境变量；内核任务需 KVM。
  • 与 DARPA AIxCC 无隶属关系：AIxCC 比「发现+补丁」，ExploitGym 比「已知 bug→exploit」。
竞赛 · 天花板

DARPA AIxCC 2025 决赛（Team Atlanta / ATLANTIS）

2025-08-08 拉斯维加斯 DEF CON 33，总奖池 2250 万美元，42 队初选留 7 队。
  • 冠军 ATLANTIS（Georgia Tech + Samsung + KAIST + POSTECH），奖金 400 万；亚军 Trail of Bits / Buttercup 300 万；季军 Theori 150 万。
  • ATLANTIS：70 个目标中找到 43 个漏洞（61%），提交准确率 91%；路线「传统程序分析 + LLM」混合，论文 arXiv:2509.14589。
  • 全场口径：7 队在 63 个合成漏洞中找到 54 个（86%）、修复 43 个；另发现 18 个真实未知 0day（6 C / 12 Java）。
  • Buttercup：全程只用非推理型 LLM，28 个漏洞、90% 准确率、181 美元/point。
  • 七套决赛 CRS 已全部开源。
开源框架

CAI（aliasrobotics/cai）

注意：CAI 不是 AIxCC 参赛队，它是 Alias Robotics 的通用攻防 Agent 框架（2025-04 开源），现已归档只读。
  • 六大支柱：Agents / Tools / Handoffs / Patterns / Turns / HITL；走 LiteLLM 路由 300+ 模型，15+ 预设多 Agent 模式。
  • 约 9.8k star；偏「LLM + 现成安全工具编排」，不做二进制反汇编 / 污点那种深度程序分析。
  • 30+ CVE 是公司多年机器人安全累计披露，不能全算 Agent 自动产出；CTF 战绩 Neurogrid #1。
真实战果标杆

Vulnhuntr（protectai/vulnhuntr）

零样本、仅 Python 代码库的 LLM 自主远程漏洞扫描器，AGPL-3.0。
  • 流程：读 README → 全文初扫 → 逐可疑点用漏洞专用 prompt 二扫 → 跨文件补调用链 → 输出 scratchpad + PoC + confidence。
  • 用 Jedi 做调用链解析，本质是静态调用链 + LLM 推理，不做动态/污点/二进制。
  • 官方样本表：扫 gpt_academic / ComfyUI / Langflow / FastChat / Ragflow / LLaVA 等 8 个热门仓库，外部口径 12+ 个生产 0day。
  • 只支持 Python、只认 LFI/AFO/RCE/XSS/SQLi/SSRF/IDOR 七类；当前 star 数未查证。
闭源 SOTA

Google Big Sleep / Project Naptime

Project Zero + DeepMind 内部 AI 漏洞研究 Agent，不开源、不公开模型。
  • 2024-10 在 SQLite 开发版发现可利用栈缓冲区下溢（当天修复、未进 release）——首个公开确认的 AI 在生产软件独立挖到真实 0day。
  • 2025-07 结合 GTIG 威胁情报，抢在在野利用前定位 SQLite CVE-2025-6965（CVSS 7.2）。
  • 后续 ANGLE CVE-2025-9478、WebKit 5 个漏洞均为媒体报道口径；官方从未公布累计 CVE 总数。
  • 模式：variant analysis 定向搜寻 + 沙箱执行，而非无差别 fuzz。

B 组 · 渗透测试与 LLM+fuzz 趋势

渗透 agent

PentestGPT（GreyDGL，USENIX Security 2024）

注意：论文是 USENIX Security 2024，不是 NDSS 2023。面向 CTF / HTB 靶机的半自主渗透研究原型。
  • 三模块各持独立 LLM 会话：Reasoning（维护渗透任务树 PTT）/ Generation（出命令）/ Parsing（解析回显）。
  • human-in-the-loop 半自主：legacy 靠人把工具输出喂回；调用 nmap/Gobuster 等现成工具，自身不重写扫描器。
  • 论文：任务完成率 80%（裸 GPT-4 仅 47%），相对 GPT-3.5 +228.6%，HTB 全球 #900；约 15.6k star。
渗透 / chatbot

HackerGPT · AutoAttacker · PentestAgent

渗透类 LLM agent 整体处于「受控靶机」阶段。
  • HackerGPT/HackerAI：本质安全 chatbot，2026-09 才加 Web CTF 浏览器自动化（靶标限 Juice Shop），~597 star。
  • AutoAttacker（arXiv:2403.01038）只做 post-breach 阶段，隔离环境评测，非端到端。
  • PentestAgent（arXiv:2411.05185）：GPT-4 端到端成功率 74.2%。所有此类评测几乎都在 CTF/HTB/Metasploitable。
LLM4Vuln 趋势

LLM 漏洞能力现状综述

学界共识：进步明显，但「跨文件 / 复杂漏洞」仍是短板。
  • LLM4Vuln（NTU，arXiv:2401.16185）建 UniVul benchmark，6 模型 × 3528 场景，实战挖到 14 个 0-day、$3,576 赏金。
  • 2025 年强模型（GPT-5/Claude Opus 4.1）在 50 个给定漏洞上检出 44–46、修复 42–43。
  • AST/数据流/RAG/代码切片能提升，但跨文件是公认难点。
LLM + Fuzz

ChatAFL · Fuzz4All · FuzzGPT

LLM 当 fuzz 输入引擎，都只做单点 fuzz，不与多 agent 编排融合。
  • ChatAFL（NDSS'24）：LLM 引导协议 fuzz，状态转移超 AFLNET 47.6%、速度 48×，但偏文本协议。
  • Fuzz4All（ICSE'24）：通用 LLM fuzzer，在 GCC/Clang/OpenJDK 发现 76 bug，47–64 个先前未知。
  • FuzzGPT（2023）：用历史 bug 引导造边缘用例，PyTorch/TF 上 76 bug、49 未知、含 11 个高优安全漏洞。

05缺点深度分析：对齐课程四项要求逐条打分

课程要求四条，逐条判定现状、缺口性质，并区分「课程约束下可接受」与「答辩前必须补」。核心结论：VulnAgent 在 ExploitGym 上是零实战、从未产出真实 CVE，这是与所有对标项目最本质的差距。

① 收集已知漏洞 PoC，分析触发 / 利用原理部分达标 · 答辩前补

现状：仓库 third_party/exploitgym/ 已引入大量 PoV（kernelctf、syzbot、v8 clusterfuzz pov），poc/service.py 有受控 replay 脚本接口。缺口：停留在「数据集摆进来」，没有形成「逐 PoC 分析触发条件 → 根因 → 利用原由」的文档化产物；加壳/混淆样本 0 finding 或仅 UNCERTAIN，说明原理分析未闭环。
判定：这一条课程约束下可接受半成品，但答辩前必须挑 3–5 个 PoC 写出结构化分析（触发输入、根因 patch、为什么能越权），否则等于没做。

② 用多智能体系统挖掘 ExploitGym 安全基准未达标 · 最致命缺口

现状：数据集目录在，但0 个任务跑通、0 份实验报告。对照图 2，即使 Claude Mythos 也只解出 157/898——ExploitGym 是「已知 bug→武器化」，不是从零找洞，门槛其实比想象低；对接只需按官方 README 起 controller+proxy 三件套并注入四个 CYBERGYM_* 环境变量。判定：这是课程点名要求，答辩前必须补，且是性价比最高的一块——哪怕只在最简单的用户态任务上跑通 1–2 个 flag，也能把「0 实战」写成「0→2」。

③ 用多智能体系统挖掘未公开漏洞未达标 · 需降预期但要有动作

现状：从未在真实大型开源项目/真实 CVE 上验证过发现能力；DeepSeek/GLM/Kimi 的 F1=1.0 只在 34 个自研教学样本上。对标：Vulnhuntr 靠「只读 Python 调用链」就挖出 12+ 生产 0day，Big Sleep 在 SQLite 挖真实内存洞——证明「小系统也能出真实成果」，关键是真去扫一个真实开源仓库。判定：课程不要求 0day 数量，但必须有「在真实 GitHub 仓库跑一遍 source_audit、列出候选、人工复核」的记录；哪怕最后都 REJECTED，也比玩具样本 F1=1.0 有说服力。

④ 提交国家漏洞库未启动 · 依赖③的真实产出

现状：0 条提交记录。判定：④ 完全寄生在 ③ 上——没有经过独立 Verification + Evidence First 背书的真实候选，就没有可提交物。课程约束下可接受：国家漏洞库（如 CNVD/CNNVD）收录有门槛和审核周期，课程设计不强求真收；但答辩前必须把「一条完整的 CANDIDATE→VERIFYING→（UNVERIFIED）→证据链→拟提交说明」走通，证明流程具备，而不是空谈。

差距本质：骨架领先，战果为零

VulnAgent 的架构差异化其实有真东西——统一漏洞 Schema + 独立 Verification 层 + Evidence First + 静态/Fuzz 联动，这些恰恰是 PentestGPT / PentestAgent（跑通即报）、ChatAFL/Fuzz4All/FuzzGPT（单点 fuzz 不编排）都缺的。问题不在设计，在于从未让这套架构面对一个真实输入跑出真实输出。评审看到的是：28k 行工程、763 测试，却没有一行实验报告来自 ExploitGym 或真实仓库。

06可执行改进优先级建议

按「课程答辩价值 ÷ 实现成本」排序，前两项做了就能把最硬的「0 实战」短板补成有故事可讲。

  1. 在 ExploitGym 上跑通 1–2 个最简单的用户态任务 P0 · 必做

    不要碰 V8/内核（要 KVM、沙箱重），先选 data/task_ids 里最简单的用户态 OSS-Fuzz 任务。按官方 README：uv sync --extra proxy → setup_data.sh 解包 → pre_run.py 起 controller/Squid/proxy → 把 VulnAgent 的 source_audit + fuzz 接进 run_agent.py 并注入四个 CYBERGYM_* 环境变量 → 即使只能复现 PoV 触发崩溃、或扩展成读 flag，也写一份实验报告：任务 ID、用了哪些 Agent、哪一步卡住、拿到什么。目标不是追 Mythos 的 157，而是从 0 → 1。

  2. 挑 3–5 个已有 PoC 写结构化原理分析 P0 · 必做

    从 third_party/exploitgym 里挑用户态 PoV，每个写：触发输入、根因 patch 前后 diff、为什么这个 patch 修了、PoV 为什么没越权而 exploit 能越权。直接回答课程要求①，也为 ④ 的证据链模板打底。

  3. 在一个真实 Python 开源仓库跑一遍 source_audit P1 · 强烈建议

    学 Vulnhuntr 路线：挑一个 star 不高、自己熟悉的 Python Web 项目，跑完整 source_audit，把所有 CANDIDATE 过一遍 Verification，无论最终 CONFIRMED 还是 REJECTED 都留记录。这同时服务课程要求③，并天然产出「一条走通的漏洞流程」供要求④演示。

  4. 把一条 CANDIDATE→VERIFICATION→证据链→拟提交说明走通 P1

    用第 3 步的任意一个候选（哪怕最后判 UNCERTAIN），完整跑 Evidence First：关联 source_location / code_snippet / fuzz_input / crash_log，由 VerificationAgent 定级，产出一份「拟提交国家漏洞库说明」草稿。证明流程具备即可，不强求真收录。

  5. （时间允许）补 C/C++/Go 跨函数污点与真实隔离 P2 · 有余力再做

    当前函数内污点、无真正网络/文件系统隔离是作者已承认的短板，但相对「0 实战」是第二位问题。答辩前不必追求，写进 future work 即可。

07同类项目设计亮点与可借鉴清单

不是全盘照搬，而是把别家被验证过的机制，落到 VulnAgent 现有模块（Planner / Supervisor / SourceAudit / FuzzAgent / VerificationAgent / Evidence / LLM Adapter）上。成本：低=1–2 天 / 中=一周级 / 高=需新子系统；并区分「答辩前值得」与「锦上添花」。

L1Vulnhuntr：分层自递归 prompt 审计低成本答辩前值得

它怎么做：读 README 摘要进上下文 → 全文初扫列可疑点 → 逐疑点喂「漏洞类型专用 prompt」二扫 → 按需跨文件拉函数补调用链 → 输出 scratchpad + PoC + 置信分（<7 忽略）。

解决的问题：一次塞全仓代码进长上下文必丢失重点；分层 + 按需检索把注意力和 token 用在刀刃上。

VulnAgent 差距：SourceAuditAgent 偏「一把梭」喂代码，缺逐疑点深钻 + 置信度分级。

可落地：把 SourceAuditAgent 改成两阶段——Stage1 产候选位置列表，Stage2 对每个候选用专属 prompt 跨文件补调用链，最终带 confidence 写进 VulnerabilityCandidate。

L2PentestGPT：推理 / 生成 / 解析三段式，各持独立会话中成本锦上添花

它怎么做：Reasoning 维护任务树决定下一步、Generation 出命令、Parsing 解析工具回显，三个 LLM 会话刻意分开以防长上下文遗忘。

解决的问题：推理与原始工具输出混在一个上下文，几轮后策略漂移。

VulnAgent 差距：FuzzAgent 把 libFuzzer 回显和推理堆在一个会话里。

可落地：FuzzAgent 内部拆「parse 子会话」——先把 libFuzzer 回显结构化成 {crashes, coverage, corpus} 摘要，再喂给推理主会话；Planner 已有任务树雏形可复用。

L3ATLANTIS：单编排器 + 职责固定模块，按目标类型裁剪组合低成本答辩前值得

它怎么做：CP-MANAGER 统一编排，C 类目标部署 Multilang+C、Java 类部署 Multilang+Java，模块间只走 API，状态机驱动路由（非自由协商）。

解决的问题：多 agent 乱序调用、不可复现。

VulnAgent 差距（其实已大半对齐）：Supervisor 已有界路由 MAX_AGENT_STEPS=15；缺的是「按 target 语言/类型选模块子集」。

可落地：Supervisor 增加路由表——target=Python 走深度审计，=C/C++/Go 走 binary+fuzz，=加壳样本先走 program_restoration 再审计。这是把现有 Supervisor 讲成亮点的最便宜方式。

L4ATLANTIS / Buttercup：patch 生成 + 「重编译→功能测试→重跑 PoV」验证闭环高成本锦上添花

它怎么做：只对去重后的唯一 PoV 请求 patch；每出一个候选就 rebuild → 跑功能测试 → 重跑原 PoV 确认崩溃消失，不过就把反馈回灌让 coder 重生成。

解决的问题：假修复、patch 破坏功能。

VulnAgent 差距：目前只发现、不验证修复。

可落地：VerificationAgent 增加「修复验证」子流程——对 CANDIDATE 生成最小 patch，重编译 + 重跑 PoV，把「崩溃是否消失」写成一条 VERIFICATION_RESULT 证据。课程不要求出补丁，做成 demo 即可。

L5ATLANTIS：按模块硬切 LLM 预算与 TPM 上限低成本答辩前值得

它怎么做：每个 CP/模块独立 API key，固定切分预算（SARIF 留 $500、Patch 25%、发现模块各 37.5%），并按模块设 TPM 上限，防单模块吃满配额。

解决的问题：成本失控、单 agent 拖垮全局。

VulnAgent 差距：LLM Adapter 统一了调用，但无 per-agent 预算/熔断。

可落地：LLM Adapter 加 per-agent token / $ 计数与熔断（某 agent 超预算即降级到 MockLLM 或停）。这是「工程成熟度」一栏最便宜的加分。

L6Buttercup：「无 PoV 不上报」保守原则 + 便宜模型只干两件事低成本答辩前值得

它怎么做：没有触发 PoV 就不报 bug、不出 patch；LLM 只用于 fuzz seed 生成和 patch 生成，其余判断力交给 tree-sitter 静态定位 + libFuzzer/Jazzer 覆盖制导。

解决的问题：高误报、贵模型乱推理。

VulnAgent 差距（架构已对齐，缺硬规则）：已有 Verification 独占定级 + Evidence First，但「无证据不得 CONFIRMED」没写成机器强制规则。

可落地：VerificationAgent 加硬校验：Evidence 里没有 FUZZ_INPUT / CRASH_LOG / SOURCE_LOCATION 等可复现证据，自动压到 UNCERTAIN。这与 AGENTS.md 的 Evidence First 完全同向。

L7Big Sleep：variant analysis（拿已知 bug 找同类模式）中成本答辩前值得

它怎么做：不做无差别全仓扫，而是拿一个已修错误模式，让 agent 在代码库里找「同类写法」的其他位置——SQLite 栈下溢就是这么被发现的，常规 fuzz 没撞到。

解决的问题：盲扫低效、漏报。

VulnAgent 差距：缺「从已知漏洞模式出发的定向检索」。

可落地：从 ExploitGym PoV / 历史 CVE 提取错误模式（如「-1 当数组索引」「未校验长度的 memcpy」），让 SourceAuditAgent 在真实 GitHub 仓库里找同类——直接服务课程要求③（挖未公开漏洞）。

L8Big Sleep / ATLANTIS：agent 工具循环 + fuzz stuck 自动喂 LLM中成本锦上添花

它怎么做：读码→假设→生成输入→跑→看 sanitizer 崩溃，阴性则修正假设；ATLANTIS 的 fuzzer 种子 2 分钟无新覆盖就把调用栈+源码 trace 喂 LLM 造新输入。

解决的问题：fuzz 卡死在低覆盖区。

VulnAgent 差距：已接真实 libFuzzer/ASan，但缺「卡住→LLM 辅助变异」的闭环。

可落地：FuzzAgent 加 stuck-detector（N 分钟无新边）→ 把崩溃/覆盖率摘要交给 LLM 生成新 seed，回喂 libFuzzer corpus。

L9CAI：显式 Handoffs + 可复用编排 Patterns中成本锦上添花

它怎么做：多 agent 之间不互调函数，而是按 LangGraph 式显式交接把任务连同上下文移交给下一个专职 agent；把「侦察→扫描→利用→报告」固化成可复用模板。

解决的问题：一个大 prompt 塞所有职责、每次从零写流程。

VulnAgent 差距：agent_runtime 已用 AgentMessage 交接，接近 Handoffs；缺的是把典型流程固化成命名 pattern。

可落地：把「源码审计」「二进制还原→审计」「fuzz→崩溃复核」固化成 Supervisor 可一键调用的命名模板（pattern），降低答辩时演示的不确定性。

L10CAI：四层 guardrail 防 prompt 注入低成本答辩前值得

它怎么做：工具回包一律包成「=== EXTERNAL DATA ONLY ===」；拦截 $(...)/反引号命令替换；拦「base64 解码即落盘执行」；一次性容器会话后重置。

解决的问题：目标程序输出里的恶意指令劫持 agent。

VulnAgent 差距：FuzzAgent 跑第三方二进制、读恶意文件 strings，注入面未隔离。

可落地：把 fuzz 回显 / 二进制 strings / 反汇编文本喂 LLM 前统一包成外部数据标记，并正则过滤命令替换模式——低成本体现安全意识，呼应 AGENTS.md 安全原则。

L11ExploitGym harness：资源硬限 + 双 agent-as-a-judge中成本答辩前值得

它怎么做：每个 agent 实例单 Docker 容器硬限 4 vCPU/8GB，出口走白名单 egress 代理；成功要过两关——抓到动态 flag + 两个独立 judge 复核「你真打的是指定漏洞而非走捷径」。

解决的问题：逃逸、作弊、误判。

VulnAgent 差距：Windows Job Object 已有进程级隔离但缺资源限额；VerificationAgent 是单方定级。

可落地：(a) Fuzz 跑第三方目标时补 CPU/内存上限与出站白名单；(b) 高风险 CANDIDATE 走「两个不同 LLM 互验」，一致才 CONFIRMED——把现有 ReviewerAgent 用成第二 judge。

L12ATLANTIS：directed fuzz 按静态危险点选 seed 优先级高成本锦上添花

它怎么做：BULLSEYE 用 LLVM pass 算跨过程 CFG 距离中心性选 landmark，在 AFL++ 上改 power schedule 把种子优先级推向危险 sink；配合 SymCC 混合执行。

解决的问题：通用 fuzz 打不到复杂路径。

VulnAgent 差距：已有符号执行引擎 + libFuzzer，但 seed 选择未利用污点 sink 信息。

可落地：给 libfuzzer.py 对接加「按静态污点 sink 距离给 seed 打分」的轻量启发式；完整 directed fuzz 留作 future work。

一句话总结

VulnAgent 的「统一 Schema + 独立 Verification + Evidence First」骨架其实已经暗合 Buttercup / ATLANTIS 的保守验证哲学；答辩前最该做的不是重写架构，而是补三条低成本硬规则：L1 分层深钻、L6 无证据不确认、L10 防注入包装，再加 L7 variant analysis 去真实仓库扫一遍——这四步同时把「0 实战」和「误报控制」两个最痛的问题一起推进。
