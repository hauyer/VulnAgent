# VulnAgent V0.2 Multi-Agent Architecture Foundation

## 1. 总体架构

```text
API / CLI / Frontend
        ↓
TaskManager → Orchestrator（Task 生命周期、持久化、DomainEvent）
                    ↓
             AgentRuntime（LangGraph）
                    ↓
       Planner → Supervisor → AgentRouter
                    ↓
 Source / Binary / optional Fuzz / Verification / Reviewer / Report
                    ↓
              Capability Protocol
                    ↓
       AnalysisContext + Evidence + AgentMessage
```

V0.2 保留 V0.1 的全部公共 Contract。LangGraph 只实现节点、条件边和受限循环，不是公共协议、数据库或业务上下文。

## 2. Orchestrator 与 AgentRuntime

`Orchestrator` 是系统级任务拥有者：读取和更新 Task、验证 TaskStatus 迁移、持久化 Evidence、保存最终 AnalysisContext，并发布任务级事件。`AgentRuntime` 是单次运行的工作流执行器：调用 Supervisor、验证路由、执行注入 Agent、聚合 AgentResult。Runtime 不直接访问仓储，不修改 TaskStatus，也不确认漏洞。

`Pipeline` 被保留为单个 Agent stage 的标准执行与合并封装，由 Runtime 动态选择，而非再维护固定阶段列表。

## 3. Agent 与 Capability

Agent 继承唯一的 `BaseAgent`，负责计划、选择能力、组织协议输入和生成结构化消息。实际源码解析、审计、二进制读取、Fuzz、验证和报告由 `contracts` 中的 Capability Protocol 完成，并由 `bootstrap.py` 注入具体 Mock。

Agent 不创建第三方 SDK，不导入 Analyzer/Fuzz/Verification/Report 的具体实现。`ToolRegistry` 以 `source.parse`、`binary.inspect`、`fuzz.execute`、`verification.verify` 等逻辑名称暴露 Adapter 边界，为后续 ToolEnabledAgent 提供基础。

## 4. RuntimeState 与 AnalysisContext

- `Task`：可持久化任务状态。
- `AnalysisContext`：一次分析的唯一业务上下文，保存 Finding、Evidence、Verification、Report、Artifact 和 AgentMessage。
- `RuntimeState`：图的临时路由状态，只保存当前/下一 Agent、步数、路由历史、消息引用、待处理动作、已完成 Agent 和运行元数据。

RuntimeState 不复制 Finding、Evidence 或 Report，因此不会形成第二套业务模型。

## 5. Supervisor 与结构化路由

允许路由由内部 `AgentRoute` Enum 限定：planner、source_analysis、binary_analysis、fuzz、verification、reviewer、report、finish。Supervisor 根据 TargetType、Finding 数量、Plan、Verification 消息和历史选择下一节点；AgentRouter 再执行枚举校验、重复次数校验和步数校验。

非法路由和超限路由不会直接执行：尚未报告时回退到 Report，已有报告时进入 Finish。源码与项目优先 Source，二进制优先 Binary；零 Finding 直接 Report；Verification 可通过结构化消息请求有限次数的补充分析。

## 6. Evidence-first 与 Verification 边界

Source/Binary discovery 在 Candidate 进入 Verification 前创建并关联 Evidence。Candidate 只保存 `evidence_ids`，完整证据仍由 Evidence Store 独立保存。模型摘要只能使用 `MODEL_REASONING_SUMMARY`，不能独立证明漏洞。

Discovery 只能输出 `CANDIDATE`。只有 Verification capability 与 VerificationAgent 边界可以产生 CONFIRMED、REJECTED 或 UNCERTAIN；Reviewer 只检查证据关联、状态一致性、Confidence、必填字段和重复 Finding，并输出结构化 REVIEW_RESULT。

## 7. LLM 抽象

业务层仍只依赖 VulnAgent 的 `BaseLLM`。Composition Root 构造 `LLMRouter` 并注入默认 `MockLLM`；核心测试不需要 API Key、网络或厂商 SDK。后续 LangChain ChatModel 兼容应在 LLM Adapter 内实现。

## 8. 循环与 Fuzz 安全

默认 `MAX_AGENT_STEPS=15`，同时限制相同路由重复次数和 Verification 补充分析次数。达到限制后安全生成报告并结束，不存在无限 Agent loop。

Fuzz 只有同时满足目标适用、`fuzz_authorized=true` 且 Planner 请求 `fuzz.execute` 时才会进入。V0.2 默认仍使用 `MockFuzzEngine`，即使授权也不执行真实目标；没有 shell、任意子进程、网络扫描、Payload 或 Exploit。

## 9. Trace 与事件

Trace 只来自 `AgentMessage` 和 VulnAgent `DomainEvent`，记录 Agent、Route、状态、结果摘要、Evidence ID 和错误，不保存或展示模型私有 Chain-of-Thought。新增内部可观测事件包括 AGENT_ROUTED、AGENT_RETRY 和 REVIEW_COMPLETED，现有 API 继续只暴露 DomainEvent。

## 10. 九人边界与扩展

P1 维护 Core、Contracts、Agent Runtime 和 Planner；P2-P9 的能力实现仍位于各自 Owner 目录。新增 Agent 时实现 BaseAgent、定义或复用公共 Capability Protocol、在 bootstrap 注入并在 Runtime 注册 Route；新增厂商或工具时只在 Adapter/LLM 边界实现。不得形成 Source↔Binary、Fuzz→Verification concrete、Report→Analyzer 或 Agent→Vendor SDK 依赖。

V0.2 当前只提供安全 Mock 闭环。真实解析器、审计算法、二进制特征、沙箱 Fuzz、验证策略、持久化后端和模型 Provider 属于后续版本，接入时不得改变上述边界。
