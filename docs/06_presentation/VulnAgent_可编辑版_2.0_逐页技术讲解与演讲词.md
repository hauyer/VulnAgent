## 一、这份讲稿怎么使用

这份文档不是要求逐字背诵。建议按下面的方法准备：

4. “指屏提示”说明演讲时应该指向 PPT 或前端的哪个位置。
5. “老师可能追问”用于准备答辩，不建议主动展开，以免超时。

整场答辩只需要反复讲清楚一条主线：

```text
选择本地授权目标
→ 多个智能体分工分析
→ 工具生成事实和证据
→ 系统形成漏洞候选
→ 独立验证与人工复核
→ 输出可追踪的审计报告
```

### 建议统一使用的简单说法

| 技术名词 | 台上可以怎样解释 |
|---|---|
| Evidence First | 不能只报答案，还必须给出可检查的“解题过程” |
| Agent | 负责一项具体工作的软件角色，例如规划、分析、验证 |
| Supervisor | 调度员，决定下一步让哪个 Agent 工作 |
| Candidate | 疑似漏洞，还没有被最终确认 |
| Evidence | 支撑结论的证据，例如地址、代码片段、工具输出 |
| Verification | 由独立模块重新检查候选是否成立 |
| 静态分析 | 只读取文件结构和代码，不启动目标程序 |
| 动态验证/Fuzz | 在明确授权和受控条件下实际运行目标并观察异常 |
| CFG | 程序可能怎样跳转和执行的“路线图” |
| 伪代码 | 反编译工具把机器指令整理成接近高级语言的可读形式 |
| SHA-256 | 文件“指纹”，用来证明分析的是哪一个文件 |
| Canary | 每条模型测试独有的标记，用来判断模型是否真的被触发 |
| Benchmark | 固定的标准测试样本，相当于统一考试卷 |

### 三句话版本的项目介绍

如果老师要求快速介绍，可以回答：

> VulnAgent 是一个面向本地授权目标的软件漏洞分析平台。它使用多个智能体组织源码分析、二进制逆向和本地大模型安全测试，但最终结论必须有工具证据并经过独立验证。V0.41 的重点是把开源大模型、加壳软件和混淆软件三类课程要求接入同一个前端闭环。

## 第 2 页：背景与问题

**建议时长：60 秒**

### 一句话结论

大模型可以帮助分析，但不能把它说出的内容直接当成漏洞事实。

### 通俗技术讲解

大模型有时会“说得很像真的”，但它可能没有真正看到程序执行过程，也可能给出不存在的函数或漏洞。这就是幻觉问题。

VulnAgent 采用 Evidence First，也就是“证据优先”。可以把它类比成数学考试：只写最终答案不够，还要有计算过程。系统会记录：

- 在哪个文件、函数或地址发现异常。
- 哪个工具产生了这个结果。
- 有哪些代码片段、调用关系或运行记录支持判断。
- 独立验证模块最后给出了什么状态。

因此系统把“发现疑点”和“确认漏洞”分开。分析模块先产生 Candidate，即漏洞候选；只有 Verification 模块能够进一步给出 `CONFIRMED`、`REJECTED` 或 `UNCERTAIN`。

### 指屏提示

- 先指“模型幻觉、证据不足”的问题区域。
- 再指 Evidence First 流程，强调“候选不等于确认”。

### 台上演讲词

> 项目的出发点是：大模型很适合帮助理解程序，但它的一段回答不能直接成为漏洞结论。模型可能出现幻觉，也经常缺少函数位置、代码片段和触发条件。我们采用 Evidence First，像检查解题过程一样记录工具输出、地址和关联证据。分析模块只能提出疑似漏洞，独立验证模块再决定确认、驳回，或者证据不足而保持不确定。

### 老师可能追问

**问：为什么会出现 `UNCERTAIN`？**

答：它表示发现了风险信号，但证据还不够强。保留“不确定”比为了结果好看而错误确认更符合安全审计要求。

## 第 3 页：系统总体设计——六层架构

**建议时长：70 秒**

### 一句话结论

系统通过分层设计，把界面、调度、分析工具和数据存储分开，便于维护和扩展。

### 通俗技术讲解

六层架构可以类比成学校实验室：

1. **界面层**像服务窗口。React 展示页面，FastAPI 接收任务。
2. **调度层**像值班老师。LangGraph 和 Supervisor 决定下一步由谁处理。
3. **Agent 层**像不同专业的小组，分别负责规划、源码、二进制、Fuzz、验证和报告。
4. **能力层**像仪器室，提供解析、逆向、证据和报告等具体工具。
5. **外部层**连接本地 Ollama、SQLite 和文件存储。
6. **基础设施层**负责配置、日志、测试和运行边界。

分层的好处是：以后增加一个新模型或替换一个反编译工具，只需要修改对应适配层，不需要把整套系统重写。

系统还统一了 Task、AgentMessage、VulnerabilityCandidate 和 Evidence 等数据结构。可以把它理解为所有模块都填写同一种“标准表格”，所以结果能够顺利传递。

### 指屏提示

- 从第 1 层向下指到第 6 层。
- 右侧如果有 Agent 和工具列表，只挑一两个例子，不要逐项读完。

### 台上演讲词

> 系统分成六层。最上面是 React 和 FastAPI，负责页面和接口；中间的 LangGraph 与 Supervisor 像调度员，决定下一步调用哪个 Agent；各个 Agent 再使用解析、逆向、Fuzz、证据和报告工具。最下面连接本地 Ollama、数据库和文件存储。这样的分层让模块职责清楚，新增模型或替换工具时，不需要破坏原来的核心流程。

### 老师可能追问

**问：为什么需要 Agent，直接按固定顺序执行不行吗？**

答：不同目标需要的步骤不同。例如源码不需要去壳，普通 PE 也不一定需要 UPX。Planner 和 Supervisor 会根据目标信息选择步骤，同时受到最大步数限制。

## 第 4 页：LangGraph 有界状态图

**建议时长：70 秒**

### 一句话结论

多智能体不是无限对话，而是一张有入口、有条件、有上限、有出口的流程图。

### 通俗技术讲解

LangGraph 可以理解为“可以根据条件跳转的流程图”。Supervisor 每次查看当前任务状态，然后选择 Planner、Source、Binary、Fuzz、Verification 或 Report 节点。

系统保存两类信息：

- `RuntimeState`：当前走到哪一步、已经走了几步、之前走过哪些节点。
- `AnalysisContext`：候选、证据、工具结果和报告等真正的业务数据。

把两者分开的原因是：流程控制不会随意修改漏洞结论，业务结果也不会干扰调度。

“有界”是这页最重要的词。系统设置最大步骤、重复路由次数和结束条件。即使某个模型一直给出不合适的建议，程序也会回退或停止，不会无限循环。

### 指屏提示

- 按照箭头从 Start 指到 Supervisor，再指向不同 Agent。
- 最后指向 End，强调流程一定有结束条件。

### 台上演讲词

> 这张图说明多个智能体怎样协作。LangGraph 可以看成一张带条件的流程图，Supervisor 是调度员，会根据任务类型和已有结果选择规划、源码、二进制、Fuzz、验证或报告节点。系统记录当前节点、执行步数和历史路径，并设置最大步数和终止条件，所以它不是无限聊天，而是能够收敛、能够追踪的工程流程。

### 老师可能追问

**问：模型能不能直接把漏洞改成已确认？**

答：不能。状态写入受到模块边界限制，只有独立 Verification 层能够确认或驳回候选。

**建议时长：65 秒**

### 一句话结论

V0.41 保留了已有能力，同时明确没有把未完成的功能包装成成果。

### 通俗技术讲解

左侧是 V0.4 已经具备的基础，包括：

## 第 6 页：三项课程测试要求

**建议时长：70 秒**

### 一句话结论

三类测试对象不同，但都使用同一套“任务—候选—证据—验证—报告”流程。

### 通俗技术讲解

课程要求可以拆成三组：

1. **开源大模型**：使用 DeepSeek R1 1.5B 和 Qwen2.5 1.5B 作为课程基线，并能发现本机其他 Ollama 模型。
2. **加壳闭源目标**：分析经过加壳保护的授权二进制文件。
3. **混淆闭源目标**：分析经过混淆保护的授权二进制文件。

加壳可以简单理解为：程序外面增加一层压缩或保护结构，原始代码进入内存后才还原。混淆则是通过改名、改写控制流或加入干扰代码，让程序更难阅读，但功能通常不变。

题目中的“任意 2 种/2 款”表示系统需要证明能够覆盖至少两个目标，并不等于每次点击必须同时上传两个文件。因此前端允许单目标运行，也允许最多六个目标批量运行。

这里的“利用验证”采用安全的本地证据验证：确认模型是否返回 Canary、确认二进制风险是否有地址和工具证据；不生成面向公网的攻击脚本。

### 指屏提示

- 从左到右分别指出大模型、加壳和混淆三张卡片。
- 指出底部统一流程，说明三类数据最终进入同一个闭环。

### 台上演讲词

> 课程要求有三类。第一类是 DeepSeek、Qwen 等本地开源大模型；第二类是经过加壳保护的授权程序；第三类是经过混淆保护的授权程序。题目所说的两种或两款是验收覆盖要求，不代表一次运行必须放两个文件。所以系统既支持单目标快速分析，也支持批量目标。三类结果最后都进入统一的候选、证据、验证和报告流程。

### 老师可能追问

**问：为什么选择 Qwen，而不是智谱或 Kimi？**

答：课程要求写的是“例如 DeepSeek、智谱、Kimi 等任意两种”。本地部署环境中选择 DeepSeek 和 Qwen，同样满足任意两种开源模型的要求，而且能够在 RTX 3060 上稳定演示。

## 第 7 页：前端八个界面与数据关系

**建议时长：60 秒**

### 一句话结论

八个页面不是互相独立的展示页，而是同一任务从创建到报告的不同观察角度。

### 通俗技术讲解

导航顺序是：

1. 漏洞测试实验室
2. 态势大屏
3. Agent 编排拓扑
4. 事件遥测
5. 证据链矩阵
6. 漏洞候选卷宗
7. 审计报告
8. API 控制台

可以把这八页理解为：

- 实验室负责“开始做实验”。
- 态势大屏负责“看总体结果”。
- Agent 拓扑和事件遥测负责“看过程”。
- 证据链和候选卷宗负责“看为什么得出这个结论”。
- 审计报告负责“形成交付物”。
- API 控制台负责“证明前端确实调用了真实后端”。

### 指屏提示

- 按编号从 1 指到 8。

## 第 11 页：二进制自主逆向工作流

**建议时长：75 秒**

### 一句话结论

智能体先判断目标特征，再选择去壳、反编译和语义分析步骤，而不是对所有文件机械执行同一套命令。

### 通俗技术讲解

这条流程可以按六步理解：

1. **目标探查**：识别 PE/ELF 格式、区段、熵值、导入表和保护信号。
2. **智能规划**：Planner 根据前一步结果决定需要哪些工具。
3. **副本去壳**：如果识别为 UPX，适配器只处理上传副本，不启动原文件。
4. **离线反编译**：radare2 提取函数、基本控制流和 `pdc` 伪代码。
5. **语义标定**：根据伪代码、导入、字符串和调用点寻找认证、加密、注册或许可证逻辑。
6. **形成候选**：Binary Agent 把工具事实组织成候选和地址证据，再交给 Verification。

熵值可以简单理解为数据看起来有多“随机”。某些高熵区段可能与压缩或加密有关，但高熵本身不能直接证明存在恶意行为或漏洞。

工具如果缺失、超时、返回坏数据或某个函数反编译失败，系统会记录真实失败原因，不用假伪代码填充页面。

### 指屏提示

- 按箭头从左到右解释六步。
- 在去壳和反编译位置说明“处理副本、默认不执行目标”。
- 最后指向证据和验证，说明逆向结果不是终点。

### 台上演讲词

> 二进制分析先识别文件格式、区段、熵值、导入表和保护特征，再由 Planner 选择分析步骤。识别为 UPX 时，工具只对上传副本去壳，不启动原程序。radare2 离线提取函数、基础控制流和 pdc 伪代码，后续模块再寻找认证、加密、注册等关键逻辑。工具失败会被如实记录，系统不会用模拟代码代替真实产物。

### 老师可能追问

**问：只看高熵就能认定加壳吗？**

答：不能。高熵只是一个信号，还要结合区段名称、入口点、导入表和工具识别结果综合判断。

## 第 12 页：可读伪代码与关键逻辑标定

**建议时长：75 秒**

### 一句话结论

### 通俗技术讲解

`BinaryReverseWorkbench` 是二进制逆向工作台，主要显示：

- 函数名称和地址。
- 每个函数对应的真实 `pdc` 伪代码。
- CFG 后继关系，也就是代码可能跳到哪些分支。

## 第 13 页：独立验证、人工复核与报告

**建议时长：70 秒**

### 一句话结论

机器结论和人工意见分别保存，既能协作，又不会互相覆盖原始记录。

### 通俗技术讲解

发现模块和验证模块是分开的。一个 Agent 发现疑点后，只能创建候选；Verification 会像“第二位检查者”一样重新检查证据。

人工复核通过独立 Review API 保存，记录：

- 复核的是哪个候选。
- 人工选择接受、驳回还是继续跟进。
- 复核说明、复核人和时间。

人工意见会进入报告，但不会偷偷覆盖机器的原始 VerificationResult。这样以后能够清楚看到“机器当时怎么判断、人工后来怎么判断”。

一个候选通常对应一条正式独立复核记录，但它可以引用多条证据。因此页面显示“一条复核记录”是正常设计，不表示只有一条证据。

4. 截取候选详情和人工标注区域。

### 截图 B：审计报告

1. 打开“审计报告”。
2. 选择同一任务。
3. 确认报告中已经出现人工复核章节。

### 指屏提示

- 先指机器状态，再指人工复核意见。
- 指向证据数量，解释“一条验证记录可以引用多条证据”。
- 最后指向报告导出按钮。

### 台上演讲词

> 分析 Agent 只能产生候选，独立 Verification 再根据证据确认、驳回或保留不确定。人工复核也单独保存，可以填写接受、驳回或需要继续检查，并记录原因和时间。机器结果与人工意见都会出现在报告中，但互不覆盖。一个候选通常只有一条正式验证结论，却可以关联多条工具证据，所以记录数量和证据数量不能混为一谈。
